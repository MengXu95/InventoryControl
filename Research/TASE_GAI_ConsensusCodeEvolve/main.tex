\begin{abstract}
Generative AI is creating new opportunities for industrial automation, but direct deployment of large language models (LLMs) as online controllers remains difficult because of cost, safety, interpretability, and reproducibility concerns. This paper proposes \emph{ConsensusCode-Evolve}, a simulator-grounded framework that uses an LLM as an offline code-evolution engine for multi-agent inventory automation. The target problem is multi-site replenishment and transshipment, a representative discrete manufacturing and supply-operation task in which local inventory agents must coordinate material movements under demand uncertainty, lead times, capacity limits, and asymmetric cost structures. Instead of asking an LLM to control the system online, the proposed method asks it to generate constrained Python policy functions for replenishment, transshipment proposal, and consensus gating. Candidate policies are validated by an abstract-syntax-tree safety checker, evaluated in a physical inventory simulator, and selected through an archive-based loop using compact numerical feedback. A consensus-seeking layer models donor willingness, receiver urgency, and fairness debt, so transshipment actions are accepted only when they satisfy both local and system-level requirements. The resulting policies are lightweight, executable without an LLM at deployment time, and directly inspectable by engineers. The paper outlines the method, safety constraints, evaluation protocol, and planned comparisons against genetic programming, heuristic, and learning-based baselines. The central hypothesis is that simulator-grounded generative code search can discover interpretable, consensus-aware inventory policies with lower token cost than online LLM agents while retaining automation-oriented robustness and deployability.
\end{abstract}

\section{Introduction}

Industrial automation increasingly requires decision-making systems that coordinate distributed assets, adapt to uncertain operating conditions, and remain interpretable to engineers. In discrete manufacturing and supply operations, material-flow decisions such as replenishment, inventory allocation, and transshipment are not merely numerical optimization tasks. They involve multiple sites or production units with local constraints, asymmetric costs, and sometimes conflicting interests. A site with surplus inventory may be asked to support another site, but such a transfer can be harmful if the donor later faces a demand surge. This makes multi-site inventory automation a natural setting for studying distributed decision-making and consensus-aware control.

Large language models (LLMs) create a new way to generate decision logic, but direct online use of an LLM as an industrial controller is difficult. Online calls add cost and latency. They also make reproducibility, safety review, and engineering inspection harder. Inventory control adds further constraints: decisions must respect material availability, capacity, lead times, order costs, and transfer costs. A useful generative method for this setting should therefore be grounded in the simulator or plant model, should produce deterministic policies for deployment, and should expose the decision logic in a form that engineers can inspect.

Recent progress in LLM-based code generation and program search suggests one promising path. AlphaCode showed that large language models can generate many candidate programs and use selection mechanisms to solve competitive programming problems \cite{li2022alphacode}. CodeRL incorporated execution feedback into code generation \cite{le2022coderl}. Self-Refine and Reflexion demonstrated that language models can iteratively improve outputs using compact feedback or verbal memory \cite{madaan2023selfrefine,shinn2023reflexion}. Voyager used LLM-generated executable code as reusable skills in an embodied environment \cite{wang2023voyager}, and Eureka showed that LLMs can write reward functions evaluated through simulation \cite{ma2024eureka}. FunSearch is particularly relevant because it combines LLM-generated programs with automatic evaluation to discover high-performing mathematical constructions \cite{romera2024funsearch}. These studies suggest that an LLM need not be the controller itself; instead, it can serve as a generator of candidate executable programs, while an external evaluator provides grounding.

This paper transfers that idea to industrial inventory automation. We propose \emph{ConsensusCode-Evolve}, a token-efficient framework in which an LLM evolves small, safe Python policy functions offline. Each candidate policy contains three functions: a replenishment policy, a transshipment proposal policy, and a consensus gate. The replenishment function determines local order quantities. The transshipment proposal function suggests pairwise material movements. The consensus gate accepts, scales, or rejects proposed transfers based on donor willingness, receiver urgency, network benefit, and fairness debt. Candidate code is statically checked before execution and then evaluated in a multi-site inventory simulator. Only compact performance summaries and selected policy code snippets are returned to the LLM for the next mutation round.

The proposed approach differs from direct LLM planning in three ways. First, the LLM is used offline, which reduces token cost and avoids dependence on a large model during deployment. Second, generated code is constrained to a small safe subset of Python, making the final policies inspectable and reproducible. Third, the method embeds autonomous multi-agent consensus seeking into the action layer, so transshipment decisions are not treated as forced centralized commands but as negotiated actions among local inventory agents.

The intended contributions are as follows:
\begin{itemize}
    \item A simulator-grounded generative code-evolution framework for multi-site replenishment and transshipment automation.
    \item A consensus-aware policy representation that separates replenishment, transshipment proposal, and agreement gating.
    \item A lightweight safety mechanism based on abstract syntax tree validation for generated industrial policy code.
    \item An evaluation protocol comparing LLM-evolved policies with genetic programming, heuristic, and learning-based baselines under cost, service, fairness, and robustness metrics.
\end{itemize}

The claims in this paper are limited to the method, the implemented prototype, and the evaluation design. Empirical superiority over baselines should be claimed only after the full experiments in Sections V and VI are completed.

\section{Background and Related Work}

\subsection{Multi-Site Inventory and Material-Flow Automation}

The problem studied in this paper belongs to multi-location inventory control and material-flow automation. A set of sites, such as plants, warehouses, production cells, or spare-parts depots, must decide when to order inventory and how to share inventory across locations. The basic inventory tradeoff is well known: high inventory reduces lost sales or service failures, but it increases holding cost and may waste capacity; low inventory saves capital, but it raises the risk of shortage. Classical inventory texts describe this tradeoff through reorder-point, base-stock, and $(s,S)$ policies under demand uncertainty and replenishment lead times \cite{zipkin2000foundations,axsater2015inventory}.

Multi-site systems are harder than single-site systems for three reasons. First, each site has a local state, but the value of an action depends on the network state. A site with high inventory may be a good donor when the rest of the network is short, but the same site may need to keep stock when its own forecast is high. Second, replenishment and transshipment decisions interact. Ordering too much can reduce future shortages but may also make transshipment unnecessary and costly. Transshipping too aggressively can lower current lost sales but create future donor shortages. Third, industrial automation must respect physical and operational constraints, including lead times, capacity, order costs, and transfer costs. These constraints make the control problem a sequential decision problem rather than a one-period allocation problem.

This paper focuses on replenishment and lateral transshipment. Replenishment brings new material into the network after a lead time. Lateral transshipment moves inventory between sites at the same echelon. Reviews of lateral transshipment models show that pooling inventory can improve service and reduce total stock, but the decision rules become difficult when demand is stochastic, costs are asymmetric, and sites differ in capacity or service pressure \cite{paterson2011lateral}. Prior work on supply-chain inventory review and control also shows that inventory decisions must be modeled as dynamic systems with uncertain demand and coupled decisions \cite{kogan2010inventory,boccadoro2008hinfinity}. In industrial automation, this difficulty is not only computational. A transfer also changes the risk exposure of the donor site. This motivates a policy representation that treats transshipment as an agreement between local agents rather than as a forced movement from a central planner.

\subsection{Production-System Modeling and Scheduling}

A second body of work studies how production and logistics systems should be modeled before decisions are optimized. Manufacturing systems are often discrete, constrained, and history dependent. Petri-net models have been used to describe production sequences and resource constraints \cite{castelnuovo2007petri}. Systems approaches to batch-discrete manufacturing model production stages, buffers, and improvement actions at the system level \cite{liu2022batch}. Stochastic continuum models have also been used for control of multi-line re-entrant manufacturing plants \cite{zhang2024reentrant}. These studies show that industrial decisions should be grounded in the physical and operational structure of the system.

Scheduling research gives a related view. In semiconductor and job-shop systems, reinforcement learning has been used for robust scheduling and real-time dynamic scheduling under changing conditions \cite{park2020semiconductor,luo2022jobshop}. Cloud manufacturing studies also use deep reinforcement learning to assign tasks when rewards are sparse and resources are distributed \cite{wang2025cloud}. These methods can react to complex system states and learn from simulation, but they usually produce scheduling policies rather than inspectable inventory-transfer code. They also do not address the donor-risk and fairness issues that appear when one site gives inventory to another. The present paper adopts the same need for simulator-grounded decisions, but studies replenishment and transshipment policies whose final form is executable code.

\subsection{Analytical and Rule-Based Inventory Policies}

The first category of methods uses analytical or rule-based policies. Representative examples include reorder-point policies, order-up-to policies, and $(s,S)$ policies. These methods are attractive because they are simple, fast, and easy for engineers to inspect. They also give strong baselines for inventory problems with regular demand and relatively simple cost structures \cite{zipkin2000foundations,axsater2015inventory}.

Their limit is that hand-designed rules often encode only a small part of the system state. A local $(s,S)$ rule may handle replenishment well for one site, but it does not naturally decide how much inventory should be moved between sites under asymmetric holding costs, shortage costs, and forecasts. Rule-based lateral transshipment policies can be added, for example by moving inventory from surplus sites to shortage sites. However, such rules often require fixed thresholds and may not capture donor risk, receiver urgency, and repeated one-way support in the same decision. In the present paper, these policies are useful as interpretable baselines and as seed policies for generative code search, but they do not provide an automatic way to design consensus-aware transfer logic.

\subsection{Optimization, Simulation, and Digital-Twin-Based Search}

The second category formulates inventory control as an optimization problem. Exact dynamic programming can be used for small systems, but the state and action spaces grow quickly with the number of sites, inventory levels, pipeline orders, and transfer decisions. For larger stochastic systems, simulation-based optimization is often used: a candidate policy is evaluated in a simulator, and a search method improves policy parameters or policy structure based on simulated performance \cite{fu2015simulation,amaran2016simulation}.

Simulation-based search fits the problem in this paper because the simulator can include lead times, lost sales, capacity, order costs, and lateral transfers directly. It also supports fair comparison among very different policy classes. Related studies use digital twins and data-driven models to support scheduling and multi-objective optimization in manufacturing systems \cite{shen2024digitaltwin,lin2026digitaltwin}. Such work is valuable because it connects decision learning to a model of the plant or process. The weakness is that simulation feedback can be expensive and noisy. A search method must decide how to use limited evaluation budget. If the policy class is too simple, the search cannot express useful coordination behavior. If the policy class is too large, many candidates are invalid, unsafe, or hard to interpret. ConsensusCode-Evolve follows the simulation-based view, but it uses an LLM to propose small executable policy programs and uses the simulator only as the judge.

\subsection{Evolutionary and Genetic Programming Policies}

The third category learns symbolic decision rules through evolutionary computation. Genetic programming (GP) evolves expression trees rather than numeric parameters \cite{koza1992genetic,poligp2008fieldguide}. This is useful for inventory automation because a GP tree can map state variables, such as inventory, forecast, capacity, and cost, to an order or transfer quantity. Multi-tree GP can represent different decisions with separate trees, for example one tree for replenishment and another tree for transshipment. Cooperative coevolution can further split a large policy into interacting components.

The strength of GP is that the learned rules are executable and more inspectable than many black-box policies. GP can also discover nonlinear combinations of state variables without requiring a differentiable simulator. These features make GP a strong baseline for this project. The limit is that GP search is usually driven by syntactic mutation and crossover. It may need many evaluations to discover higher-level program structure, such as a donor-protection rule followed by a fairness correction. GP trees also tend to express decisions as direct mappings from state to action. They do not naturally separate a transshipment proposal from a later agreement gate unless this structure is built into the representation.

ConsensusCode-Evolve keeps the useful idea of executable symbolic policies, but replaces random program edits with LLM-generated code mutations constrained by an explicit API. This does not remove the need for simulation evaluation. Instead, it changes the source of candidate programs while keeping the simulator as the authority on performance and feasibility.

\subsection{Learning-Based Inventory Control}

The fourth category uses reinforcement learning (RL) and deep RL to learn policies through interaction with a simulated environment. RL is a natural fit for sequential inventory problems because actions affect future states, and the objective is cumulative cost or reward \cite{sutton2018reinforcement}. Deep RL methods, including value-based and policy-gradient methods, can represent complex policies in large state spaces \cite{mnih2015human,schulman2017ppo}. In inventory systems, RL can learn from simulated demand trajectories and can adapt to nonlinear interactions among replenishment, shortages, and transfers.

The main strength of RL is flexibility. It can use rich state information and optimize long-run reward directly. Its main limits for the present paper are deployment trust and interpretability. A neural policy can be difficult to inspect, and small changes in scenario design may require retraining or careful validation. In addition, direct RL does not by itself explain whether a transfer is fair to the donor or acceptable to both sites. These issues are important in automation settings where engineers must understand why a material movement is recommended. For this reason, RL is best treated here as a learning-based baseline rather than as the central design model.

\subsection{Multi-Agent Coordination and Consensus Seeking}

The fifth category studies distributed decision-making and consensus among agents. Consensus algorithms are widely used in multi-agent control to align decisions or estimates through local interaction \cite{olfati2007consensus}. Agent-based scheduling has also been studied through bidding languages that let agents express requirements during scheduling \cite{wang2013bidding}. Human-machine collaborative systems in intelligent manufacturing further show that industrial decision support must be understandable to people who review or modify the system output \cite{wei2025humanmachine}. In supply and inventory settings, the same idea appears in a practical form: a local unit may not want to give up inventory unless the transfer is justified by system benefit and does not create unacceptable local risk. Thus, the decision is not only ``how much should move?'' but also ``should the donor agree?'' and ``is the repeated pattern of support acceptable?''

This view is closely related to lateral transshipment. A centralized model can optimize all transfers from a network perspective, but industrial operations often contain local ownership, local service targets, and different risk exposure. A consensus-aware policy can make these tensions explicit. In this paper, the consensus gate is not a general communication protocol. It is a small executable function that accepts, scales, or rejects a proposed transfer using donor state, receiver state, and transfer history. This choice is deliberately modest. It gives the policy a place to encode donor willingness, receiver urgency, and fairness debt without claiming that a full negotiation protocol has been solved.

\subsection{LLM Agents, Code Generation, and Program Search}

The final category is generative AI for executable decision logic. Recent work shows that LLMs can generate code, improve outputs using feedback, and participate in program search. AlphaCode generated and filtered many candidate programs for competitive programming \cite{li2022alphacode}. CodeRL used execution feedback to improve code generation \cite{le2022coderl}. Self-Refine and Reflexion showed that compact feedback can guide iterative improvement \cite{madaan2023selfrefine,shinn2023reflexion}. Voyager used generated code as reusable skills in an embodied environment \cite{wang2023voyager}. Eureka used LLM-generated reward code evaluated in simulation \cite{ma2024eureka}. FunSearch combined LLM-generated programs with automatic evaluation to find high-performing constructions \cite{romera2024funsearch}. Related optimizer-style prompting methods also show that LLM outputs can be improved through iterative candidate generation and scoring \cite{yang2023opro,fernando2023promptbreeder}.

These studies suggest a useful direction for industrial automation: the LLM does not need to act as an online controller. It can instead propose candidate programs offline, while a task simulator checks whether those programs work. This separation is important for inventory automation because online LLM calls are costly, hard to reproduce exactly, and difficult to certify. However, existing LLM code-generation work is usually not designed around inventory physics, lateral transshipment, or local agreement among industrial agents. It also often assumes that generated programs are judged by unit tests or benchmark scores, whereas this paper judges policy code by stochastic simulator performance and operational metrics.

\subsection{Research Gap}

The literature above leaves a clear gap. Classical policies are simple and inspectable, but they have limited ability to express adaptive consensus-aware transshipment. Optimization and simulation-based methods can evaluate realistic systems, but they need a policy representation that is expressive and still safe. GP provides executable symbolic rules, but its edits are mostly syntactic and may struggle to create structured agreement logic efficiently. RL can learn complex behavior, but the resulting policies are often hard to inspect and may not expose donor risk or fairness. LLM program search can generate meaningful code, but it has not been adapted to safe, simulator-grounded, multi-site inventory automation with explicit transshipment consensus.

This paper addresses that gap by combining three ideas: constrained executable policy code, simulator-based evaluation, and a consensus gate for lateral transshipment. The result is an offline generative code-search method whose deployed policy is a small Python program, not an online LLM agent.

\section{Problem Definition}

This paper studies the replenish-and-transship version of the multi-site inventory management problem implemented in the simulator. The system contains several inventory sites that face uncertain, time-varying demand. At each decision period, the controller chooses replenishment quantities and lateral transshipment quantities. The purpose is to reduce inventory operating cost while keeping transfers feasible and avoiding policies that repeatedly expose the same donor site to shortage risk. \subsection{System State and Demand}

We consider a finite-horizon periodic-review system with $N$ sites and decision periods $t=1,\ldots,T$. The current simulator supports the two-site and three-site cases. At the beginning of a decision period, the policy observes a state $S(t)$ containing local site information and pairwise transshipment information. For each site, the local information includes current inventory, holding cost, lost-sales cost, storage capacity, production-capacity parameter, fixed and unit ordering costs, the first pipeline order value, two demand forecasts, and transshipment cost parameters. Thus, the forecast horizon exposed to the policy is $H=2$ in the implemented simulator.

For synthetic scenarios, the simulator first samples a time-varying demand mean for each site and period. The realized demand $D_i(t)$ is then sampled from a Poisson distribution with that period-specific mean. The forecast value $E_i(t)$ used by the policy is the sampled mean of that demand distribution. For test scenarios based on historical demand records, the simulator uses the provided demand sequence and uses the same sequence as the forecast record. In both cases, future realized demand is not known when the policy chooses the action.

\subsection{Decision Variables and Action Structure}

At each period, the policy chooses a replenishment vector and a transshipment vector. The replenishment vector is
\begin{equation}
    \mathbf{x}(t)=\left[x_1(t),\ldots,x_N(t)\right],
\end{equation}
where $x_i(t)$ is the order quantity for site $i$. Orders are not available immediately. They enter the pipeline and arrive after the replenishment lead time $L_o$.

The transshipment vector contains one signed quantity for each unordered site pair. For a pair $(i,j)$ with $i<j$, $q_{ij}(t)>0$ denotes a transfer from site $i$ to site $j$, while $q_{ij}(t)<0$ denotes a transfer from site $j$ to site $i$. For two sites, the action contains one transshipment quantity. For three sites, the action contains quantities for pairs $(1,2)$, $(1,3)$, and $(2,3)$.

The complete action is therefore
\begin{equation}
    \mathbf{d}(t)=\left(\mathbf{q}(t),\mathbf{x}(t)\right),
\end{equation}
where the transshipment part appears before the replenishment part in the simulator action vector.

\subsection{Inventory Transition}

For each site, an outstanding order arrives at the start of the simulator step. The inventory after order arrival is capped by storage capacity:
\begin{equation}
    \bar{I}_i(t)=\min\{Cap_i, I_i(t)+A_i(t)\},
\end{equation}
where $A_i(t)$ is the pipeline order that arrives in period $t$. Demand is then realized and subtracted:
\begin{equation}
    \tilde{I}_i(t)=\bar{I}_i(t)-D_i(t).
\end{equation}

After this demand update, lateral transshipments are applied. A proposed transfer is executed only if the donor has enough available inventory at the point where the transfer is checked. If the donor inventory is insufficient, the simulator sets that transfer to zero. Let $Q_i(t)$ denote the net inventory change at site $i$ caused by all accepted transshipments in period $t$. The inventory after transshipment is
\begin{equation}
    I_i^{+}(t)=\tilde{I}_i(t)+Q_i(t).
\end{equation}

If $I_i^{+}(t)$ is positive, the site pays holding cost. If $I_i^{+}(t)$ is negative, the shortage is charged as lost sales and the inventory carried to the next period is reset to zero:
\begin{equation}
    I_i(t+1)=\max\{0,I_i^{+}(t)\}.
\end{equation}
The new replenishment decision $x_i(t)$ is then stored in the pipeline and becomes available after the lead time.

\subsection{Feasibility Constraints}

The simulator enforces simple feasibility rules. Replenishment quantities are nonnegative after policy adaptation and are capped before entering the pipeline. In the current simulator step, any replenishment quantity above site capacity is reduced to $Cap_i$:
\begin{equation}
    0\leq x_i(t)\leq Cap_i.
\end{equation}
For LLM-generated policies, the adapter first clips order quantities to a nonnegative range before the simulator applies its own capacity cap.

Transshipment feasibility is checked through donor availability. For each proposed pairwise transfer, the donor must have enough inventory to cover the requested movement after prior transfers in the same period have been considered. Otherwise, that pairwise movement is not executed. This rule prevents the simulator from creating negative donor inventory through transshipment alone, although a site may still have negative inventory after demand if it faces shortage before receiving enough transfer support.

\subsection{Cost and Objective}

The one-period cost contains three parts: transshipment cost, holding and lost-sales cost, and order cost. The transshipment cost is
\begin{equation}
    C_t^{tr}=\sum_{(i,j)} \left(c^{tr}|q_{ij}^{acc}(t)| + K^{tr}\mathbb{I}\{|q_{ij}^{acc}(t)|>0\}\right),
\end{equation}
where $q_{ij}^{acc}(t)$ is the accepted transfer after feasibility checking. The holding and lost-sales cost is
\begin{equation}
    C_t^{hl}=\sum_{i=1}^{N}\left(h_i\max\{I_i^{+}(t),0\}+b_i\max\{-I_i^{+}(t),0\}\right).
\end{equation}
The order cost is
\begin{equation}
    C_t^{ord}=\sum_{i=1}^{N}\left(a_i x_i(t)+k_i\mathbb{I}\{x_i(t)>0\}\right).
\end{equation}
The total period cost is
\begin{equation}
    C_t=C_t^{tr}+C_t^{hl}+C_t^{ord}.
\end{equation}

Given a policy $\pi$, the simulator evaluates the average cost over one episode:
\begin{equation}
    J_T(\pi)=\frac{1}{T}\sum_{t=1}^{T}C_t.
\end{equation}
The optimization goal is to find a policy with low expected average cost across demand realizations and test scenarios:
\begin{equation}
    \min_{\pi}\;\mathbb{E}\left[J_T(\pi)\right].
\end{equation}

The evaluation also records service and coordination measures, including stockout proxy count, accepted transfer count, rejected transfer count, and fairness debt. Fairness debt is computed in the current prototype as the sum of absolute net pairwise transfers over the episode. These measures do not replace the cost objective. They are used to judge whether a low-cost policy achieves its performance through reasonable coordination behavior.

\section{Proposed Method}

\subsection{Framework Overview}

ConsensusCode-Evolve is an offline generate--validate--simulate--select loop. The LLM is used only during design time. It receives a compact summary of previous policy performance and writes new candidate policy code. Each candidate is checked by a static safety validator before it is executed. Valid candidates are then evaluated in the inventory simulator. The best policies and their metrics are archived and used to construct the next prompt.

The method has four design principles. First, the deployed controller must not depend on an LLM call. After search, the selected policy is ordinary Python code. Second, the policy representation must separate local replenishment, transfer proposal, and transfer agreement. This separation makes the transshipment logic easier to inspect. Third, the simulator, not the LLM, decides whether a policy is good. Fourth, generated code must be restricted to a small deterministic subset of Python.

\subsection{State Representation}

The current implementation converts simulator arrays into dictionaries before calling the policy code. For replenishment, the site state contains the site index, inventory level, holding cost, lost-sales cost, capacity, production capacity, fixed and unit order costs, pipeline inventory, two forecast values, and transshipment costs. For transshipment, the state of a source-target pair contains both sites' inventory, costs, capacity, pipeline inventory, and forecasts. The global state contains the current period, episode length, number of sites, total inventory, total forecast, average inventory, inventory imbalance, and forecast imbalance.

This dictionary representation is used for two reasons. It gives generated code meaningful variable names, which improves readability. It also hides simulator internals from the LLM. The LLM does not receive direct access to the environment object, files, random generators, or external libraries.

\subsection{Policy-Code Representation}

ConsensusCode-Evolve represents an inventory policy as three constrained Python functions:
\begin{itemize}
    \item \texttt{replenishment\_policy(site\_state, global\_state)} returns a nonnegative order quantity for one site.
    \item \texttt{transshipment\_proposal(source\_state, target\_state, global\_state)} returns a signed or directional proposed transfer quantity.
    \item \texttt{consensus\_gate(source\_state, target\_state, proposed\_quantity, history)} returns the accepted transfer quantity after agreement filtering.
\end{itemize}

The first function is called once for each site and returns the replenishment quantity. The second function is called for a pair of sites and returns a proposed signed transfer. In the implementation, a nonnegative proposal means the first site is the donor and the second site is the receiver; a negative proposal reverses the direction. The third function receives the selected source, target, proposed quantity, and transfer history. It returns the accepted quantity. The adapter clamps the accepted quantity to the interval between zero and the proposed quantity and rounds the final action before passing it to the simulator.

This representation differs from a direct action policy. A direct policy would output an order and transfer vector in one step. Here, transshipment is split into proposal and agreement. This is useful because an LLM-generated proposal may identify an imbalance, while the consensus gate can still reject or reduce the transfer if the donor is unsafe or if pairwise transfer history is unbalanced.

\subsection{Consensus-Seeking Transshipment}

For each potential pairwise transfer, the framework first computes a proposed quantity and then applies a consensus gate. The gate is interpreted as a local agreement mechanism. A typical hand-designed form is
\begin{equation}
    q_{ij,t}^{\mathrm{acc}} = q_{ij,t}^{\mathrm{prop}} \cdot w_{i,t}^{\mathrm{donor}} \cdot u_{j,t}^{\mathrm{receiver}} \cdot f_{ij,t}^{\mathrm{fair}},
\end{equation}
where $q_{ij,t}^{\mathrm{prop}}$ is the proposed transfer from site $i$ to site $j$, $w_{i,t}^{\mathrm{donor}}$ measures donor willingness, $u_{j,t}^{\mathrm{receiver}}$ measures receiver urgency, and $f_{ij,t}^{\mathrm{fair}}$ penalizes repeated one-way support. These terms may be hand-designed in seed policies or generated directly by the LLM as executable code.

Donor willingness can depend on the donor's inventory, forecast, capacity, and shortage cost. Receiver urgency can depend on low inventory, high forecast, and high lost-sales cost. The fairness term can use transfer history to reduce repeated support in the same direction. The current prototype stores the net transfer for each site pair, the accepted transfer count, and the rejected transfer count. These variables are simple, but they make the agreement logic observable.

This structure is important for industrial automation because it prevents the GAI system from generating opaque transfer commands. Each accepted movement can be inspected in terms of donor safety, receiver need, and transfer history. The paper does not claim that this gate solves general multi-agent negotiation. It is a lightweight consensus layer for inventory transshipment.

\subsection{Safe Generative Code Search}

The LLM is used only between simulation batches. In each round, the algorithm provides a compact prompt containing the allowed API, available state keys, safety rules, the scenario name and seed, the current top policy scores, and selected policy source code. The score table includes fitness, transshipment cost, holding/lost-sales cost, order cost, stockout proxy count, accepted transfer count, rejected transfer count, and fairness debt. The LLM is asked to generate a small fixed number of deterministic candidate policy files. The current prototype asks for three candidates per round.

Before simulation, each candidate is checked by an abstract-syntax-tree validator. The current safe subset allows only top-level definitions of the three required functions. It permits assignments, returns, conditionals, arithmetic, Boolean expressions, comparisons, dictionary indexing, constants, and calls to \texttt{abs}, \texttt{min}, \texttt{max}, and \texttt{round}. It disallows imports, file operations, network access, random calls, classes, decorators, attributes, list or dictionary construction, unexpected functions, and dunder names. Candidates that fail validation are rejected without execution.

The safety checker is not a full sandbox. It is a first filter that prevents common unsafe or non-reproducible generated code patterns before simulator evaluation. \subsection{Evolution Loop}

The search loop starts from human-written seed policies. These seeds are not expected to be optimal. Their purpose is to provide the LLM with valid examples of the API and with initial behavior for comparison. After evaluation, valid candidates are sorted by fitness and stored with source code and metrics. The archive is then used to build the next mutation prompt.

\begin{algorithm}[t]
\begin{algorithmic}[1]
\STATE Initialize archive $\mathcal{A}$ with seed policy files.
\STATE Validate each seed policy with the AST checker.
\STATE Evaluate each valid seed policy in the simulator.
\STATE Store source code and metrics in $\mathcal{A}$.
\FOR{round $r=1,2,\ldots,R$}
    \STATE Select the top $k$ archived policies by fitness.
    \STATE Build a compact prompt with API rules, state keys, metrics, and selected source code.
    \STATE Ask the LLM to generate $m$ candidate policy files.
    \FOR{each generated candidate $p$}
        \STATE Run AST validation on $p$.
        \IF{$p$ is valid}
            \STATE Evaluate $p$ in the inventory simulator.
            \STATE Add source code and metrics to $\mathcal{A}$.
        \ELSE
            \STATE Record the validation error and reject $p$.
        \ENDIF
    \ENDFOR
\ENDFOR
\STATE Return the selected archived policy for deployment or further testing.
\end{algorithmic}
\caption{Offline ConsensusCode-Evolve search loop.}
\label{alg:consensus-code-evolve}
\end{algorithm}

In the current implementation, $k=3$ top policies are included in the prompt and $m=3$ new candidates are requested. The archive is stored as JSON and CSV files under the research output directory. Generated candidates can be supplied either as separate Python files or as fenced Python blocks in a response file, which the mutation loop extracts before validation.

The evaluator, rather than the LLM, determines whether a candidate is useful. This is a key difference from direct LLM planning. The LLM may suggest an action rule, but only simulator performance and validation decide whether the rule enters the archive.

\subsection{Training, Inference, and Deployment}

The method has a design-time phase and a deployment phase. During design time, the LLM generates policy-code candidates, and the simulator evaluates them. This phase may use several scenarios, random seeds, and stress tests. During deployment, the selected policy is executed directly as Python code. No LLM call is needed to choose orders or transfers.

At each deployment decision period, the simulator or industrial control system builds the state dictionaries, calls \texttt{transshipment\_proposal} and \texttt{consensus\_gate} for candidate transfer pairs, then calls \texttt{replenishment\_policy} for each site. The resulting action vector is passed to the inventory system. Because the policy is small code, an engineer can inspect thresholds, arithmetic expressions, and conditionals before use. \subsection{Differences from Existing Methods}

ConsensusCode-Evolve differs from the method categories reviewed in Section II in several concrete ways. Compared with classical inventory rules, it searches over generated policy code rather than fixing thresholds by hand. Compared with GP, it asks an LLM to make semantic code edits under an API, while still relying on simulation for selection. Compared with RL, it produces a small inspectable policy program instead of a neural controller. Compared with online LLM agents, it removes the LLM from the control loop and uses it only as an offline generator. Compared with ordinary LLM code generation, it evaluates candidates in an inventory simulator and includes a consensus gate tailored to transshipment.

\section{Experimental Design}

\subsection{Research Questions}

The experiments are designed to answer four questions.
RQ1 asks whether LLM-evolved policy code can reduce average inventory cost compared with rule-based, GP-based, and learning-based baselines under the same simulator. RQ2 asks whether the consensus gate changes transshipment behavior in a useful way, measured by accepted transfers, rejected transfers, fairness debt, and stockout proxy counts. RQ3 asks whether the method uses LLM calls efficiently, measured by the number of generated candidates, token budget, and valid-policy rate. RQ4 asks whether the selected policies remain stable under changes in demand level, holding and lost-sales costs, and network size.
